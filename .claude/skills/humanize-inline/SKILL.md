# humanize-inline — AI臭さを消すインライン道具

article-humanizer の診断・リライトロジックから Google Docs/Sheets 依存を取り除き、テキストを直接受け取ってリライト済みテキストを返す形に再構成したもの。

## 入出力契約

### 入力

呼び出し元（人間 or 他スキル）から、次のいずれかの形で渡される:

1. **プレーンテキスト**: 1本の文章を humanize する
2. **章IDマップ**: `{ "1": "章1の本文", "2": "章2の本文", ... }` の形で複数章をまとめて humanize する（章境界をまたいだリライトはしない）

加えて、文体・トーンの希望（例: 「カジュアルなブログ調」「ですます調だけどフランクに」）を初回に1度だけ受け取る。トーンが事前に判明していれば呼び出し元から渡してもよい。

### 出力

入力と同じ形（プレーン or マップ）で、humanize 済みテキストを返す。

- 入力がプレーンなら → humanize 済みプレーンテキスト
- 入力が章IDマップなら → 同じキーセットで、各値が humanize 済みテキストになっている

## ワークフロー

### Step 1: 入力テキストの確認

呼び出し元から渡されたテキストを確認する。

- プレーンテキストか章IDマップかを判別する
- 章IDマップの場合は章数を出す: 「{N}章ぶんのテキストを humanize します」
- テキストが空 or 極端に短い（30字未満）章があれば、その章はスキップする旨を伝える

### Step 2: AI臭い箇所の診断

入力されたテキストを分析し、**AI臭い箇所を番号付きリストで提示**する。

章IDマップの場合は章ごとに区切って提示する。例:

```text
分析しました。

【第1章: 結論】
① 「〜について解説します」 → 冗長な前置き
② 「〜は非常に重要です」 → AI定型表現

【第2章: それ、本当？】
③ 「まず〜。次に〜。さらに〜。」 → 構文が単調
④ 全体的に百科事典的 → 体験談を入れたい

どこを直しますか？番号で選んでください（例: 「②と③」「全部」「①以外」）。
```

#### 診断の観点

- 「〜について解説します」「〜を詳しく見ていきましょう」等の冗長な前置き
- 「〜は非常に重要です」「〜という観点から」「〜において」等のAI定型表現
- 同じ構文の繰り返し（「まず〜。次に〜。さらに〜。最後に〜。」）
- 具体性のない一般論（「多くの人が〜」「近年〜」）
- 不自然な網羅感（すべてのセクションが同じ粒度で均等に並ぶ）
- 感情・体験の欠如（誰の視点でもない、百科事典的な記述）
- 見出しが「{KW}とは」「{KW}のメリット」「{KW}の注意点」パターンの羅列
- まとめが本文の要約の繰り返しになっている

#### 診断の品質基準

- 箇所数は正直に出す。多すぎても少なく見せない
- 各箇所に「どこ」「何が問題か」「どう直すと良いか」を1行ずつ書く
- 問題がない部分は指摘しない（全部AI臭いとは言わない）
- 良い部分があれば「ここは自然で良いですね」と伝えてもよい

### Step 3: ユーザーが直す箇所を選ぶ

返答パターン:

- 「②と③と⑤」→ 選んだ箇所だけ対応
- 「全部」→ 全箇所対応
- 「③は自分で書くからスキップ」→ 残りだけ対応
- 「①はそのままでいい」→ ①以外を対応

### Step 4: 選んだ箇所に対してヒアリング

**直す箇所が決まってから**、その箇所に対してピンポイントでヒアリングする。

#### 4-1: 文体・トーン（初回のみ・呼び出し元から未指定の場合）

```text
リライトの文体はどんな感じにしますか？

例:
- 「カジュアルなブログ調（〜だよね、〜なんです）」
- 「ですます調だけどフランクに」
- 「友達に話すようなノリ」

ひとことで大丈夫です。
```

呼び出し元（script-pipeline 等）からトーンを引数として受け取っている場合は、この質問をスキップする。

#### 4-2: 体験談・具体例（該当箇所がある場合）

体験談が効く箇所がある場合、**その箇所を具体的に指して**聞く:

```text
③のキーワード選定のところ、体験談を入れると一気に人間っぽくなります。

たとえば:
- 「最初はキーワード選定で大失敗した話がある」
- 「クライアントでこういう成功例がある」
- 「特にないけどいい感じにして」

何かありますか？なければAIがそれっぽいエピソードを提案します。
```

複数箇所で体験談が必要な場合はまとめて聞いてよい。

### Step 5: 修正案の提示（before/after）

各箇所について**元の文 → 修正案**の形で提示する。

```text
修正案です:

---
② [H2: キーワード選定の重要性]
元: 「SEO対策は非常に重要です。適切なキーワード選定を行うことで、
     検索エンジンからの流入を大幅に増やすことができます。」

→ 「正直、SEO対策ちゃんとやるまで、記事書いても月10PVとかでした。
    キーワード選定を変えただけで、3ヶ月で月3,000PVまで伸びた。
    やるかやらないかで、ここまで差が出ます。」

---

採用/修正/却下を教えてください。
（例: 「②OK、③もう少しフランクに、⑤は自分で書く」）
```

#### 修正案の品質基準

- **before/after を必ず並べる**: 何が変わったか一目で分かるように
- **元の情報は保持する**: 事実関係やポイントは変えない。言い方だけ変える
- **人間っぽさの技法を使う**:
  - 不完全さを残す（完璧に整理しすぎない）
  - 一人称の視点（「私は〜」「僕の場合は〜」）
  - 読者への語りかけ（「あなたも〜しませんか？」）
  - 感情を込める（「正直、最初は全然ダメだった」）
  - 具体的な数字・固有名詞
  - 段落の長さにばらつき
- **元の文を否定しない**: 「ダメな文章」ではなく「こう変えるともっと良くなる」

#### 絶対やらないこと

- 元テキストの構成を勝手に変える（ユーザーが選んだ箇所以外は触らない）
- before/after を見せずにいきなり反映する
- 全箇所を同じパターンで書き直す（体験談一辺倒にしない）
- AIっぽい定型表現で置き換える（本末転倒）
- **章境界をまたいだリライトをしない**: 章IDマップで渡された場合、各章は独立して扱う

### Step 6: ユーザーの承認・修正

返答パターン:

- 「全部OK」→ Step 7へ
- 「②OK、③もう少しカジュアルに」→ ③を修正して再提示
- 「⑤は自分で書くからそのままにして」→ ⑤を元のまま残す
- 「②の体験談、実際は半年で5,000PVだった」→ 事実を反映して修正

修正依頼があれば、その箇所だけ再提示する。全体を出し直さない。

### Step 7: 結果を呼び出し元に返す

承認された修正を元テキストに反映した全文を、入力と同じ形（プレーン or 章IDマップ）で呼び出し元に返す。

- 変更箇所のみ差し替え。他の部分はそのまま
- 章IDマップの場合は、すべての章IDを含めて返す（変更がなかった章はそのままの値）

返却例（プレーン）:

```text
✓ humanize 完了。以下が humanize 済みテキストです:

{ここに全文}
```

返却例（章IDマップ）:

```text
✓ humanize 完了。{N}章ぶんを処理しました。

【第1章: 結論】
{humanize 済みテキスト}

【第2章: それ、本当？】
{humanize 済みテキスト}

...
```

呼び出し元（script-pipeline）がこの出力を取り込んで、`/api/script-draft` に POST する。**humanize-inline 自身は API を叩かない**（道具に徹する）。

## 基本姿勢

- **道具に徹する**: テキストを受け取り、humanize 済みテキストを返すだけ。API 呼び出しやファイル書き込みは呼び出し元の責務
- **原型をリスペクト**: 入力テキストを壊さない。直す必要がある箇所だけ直す
- **ユーザーが主導**: 診断と提案をする。決めるのはユーザー
- **before/after を必ず見せる**: 何がどう変わるか、常に透明にする
- **具体的に聞く**: 「何か体験談ありますか？」ではなく「③のこの部分に体験入れると良いけど何かある？」
- **量より質**: 修正箇所が少なくても、的確なら価値がある
