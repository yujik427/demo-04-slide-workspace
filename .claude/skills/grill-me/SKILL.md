# Grill Me

ユーザーの計画・設計・原稿を徹底的にインタビューし、決定ツリーの各分岐を1つずつ潰して共通理解に到達する。実装には入らない。ファイルも作らない。質問して理解を深めるだけ。

## 基本ルール

- **1問ずつ聞く。** まとめて質問攻めにしない
- **必ず推奨案を添える。** 「AとBどっち？」ではなく「Aがおすすめ、理由はこう。どう思う？」
- **コードベースが関連する場合は、コードで分かる事は聞かない。** Read/Grep/Glob で先に調べる
- **ユーザーが考えていない箇所を掘る。** 自明な確認は省く
- **決定の依存関係を順に解く。** Aが決まらないとBが決まらない、という順序で進める
- **専門用語は解説しながら進める。** 新卒社会人にも分かる粒度で。馴染みのない概念は必ず注釈を添える

## Step 1: 入力を理解する

ユーザーが持ち込んだ計画・設計・アイデア・原稿テーマを読む。

**まず入力タイプを識別する**(これを間違えると的外れな観点で詰めてしまう):

- **実装系**(計画・設計・コード・システム構築) → Step 2 の「実装系の観点表」を使う
- **原稿系**(販売文・LP・スライド原稿・応募文・SNS文・LINE配信文・メルマガ・ブログ・自己紹介文など、文章を書く案件) → Step 2 の「原稿系の観点表」を使う

どちらか曖昧な場合は、最初にユーザーに「これは ① システム/設計を詰める話 / ② 文章原稿を詰める話、どちらですか?」と確認してから進む。

コードベースに関連する場合は Read/Grep/Glob で現状を把握する。自分で調べて分かる事は自分で調べる。

## Step 2: 決定ツリーを洗い出す

入力タイプに応じた観点表で「何を決める必要があるか」を列挙する。

### 実装系の観点表(計画・設計・システム)

| 観点 | 深掘りすべき問い |
|------|----------------|
| **ゴール** | 誰が、何のために使うか。成功の定義は何か |
| **スコープ** | やる事とやらない事の境界はどこか |
| **UI/UX** | ユーザーにどう見えるか。既存UIとの整合性 |
| **データ** | 入出力、既存データ構造との関係、マイグレーションの要否 |
| **状態・同期** | 誰が真実の情報源か。競合時の扱い |
| **エッジケース** | 例外、境界条件、エラー時の振る舞い |
| **トレードオフ** | 複雑さ vs シンプルさ、速度 vs 正確さ |
| **非機能** | パフォーマンス、互換性、セキュリティ、権限 |
| **ロールアウト** | 段階的公開、フィーチャーフラグ、ロールバック |

### 原稿系の観点表(コピーライティング・販売文・スライド原稿)

**上から順に依存している**(=上が決まらないと下も決まらない)。

| 観点 | 深掘りすべき問い |
|------|----------------|
| **ターゲット** | 誰に向けて書くか。1人に絞れているか。年齢・職業・状況・悩み |
| **メイン訴求軸** | この原稿の「柱」。何を一番アピールするか。差別化の核 |
| **サブ訴求** | メインを支える脇役の素材。構成内でどう使い分けるか |
| **トーン** | 冷静 vs 熱量高、真面目 vs カジュアル、信頼系 vs 煽り系。情報商材臭との距離感 |
| **構成フレーム** | PASONA / Before-After / AIDA / 疑問解消型 / 証拠先行型 など。どの心理プロセスでなぞるか |
| **骨格** | 何枚(スライド)/何段落(文章)、各パーツの役割と順序 |
| **フック** | 冒頭の引き(掴み)。断言系/数字提示系/問いかけ系/結論先出し系 |
| **反論処理** | 読み手が抱く不安・疑問のリスト化と回答の置き方 |
| **CTA** | 取らせたい行動(申込/相談/登録)、1段階か2段階か、動線設計 |
| **数字優先順位** | 使える数字のうち、どれを一番強く打つか。1日◯円分解などの見せ方 |

依存関係の典型: **ターゲット → メイン訴求 → サブ訴求の扱い → トーン → 構成フレーム → 骨格 → フック/CTA/反論処理**

## Step 3: 1問ずつグリルする

選択肢で質問するツール（実行環境で利用できるもの）を使って1問ずつ聞く。依存関係の上流から順に進める。

### 良い質問 / 悪い質問

悪い例: 「認証方式どうします？」
良い例: 「既存のSupabase Auth をそのまま使い、メール+Google の2方式に絞るのがおすすめです。理由は、新しく認証基盤を足すと運用が二重化するためです。どう思いますか？」

悪い例: 「エラー処理はどうしますか？」
良い例: 「ネットワーク断の場合、楽観更新（先にUIを変えて後でサーバーに送る）で、失敗時にトーストで通知+ロールバックがおすすめです。他のページと挙動が揃います。気になる点はありますか？」

悪い例: 「ターゲットは誰ですか？」
良い例: 「副業で月10万円稼ぎたい会社員に1人絞るのがおすすめです。理由は『2件で全額回収』の訴求が一番直接刺さる層で、価格帯とも合うためです。どう思いますか？」

悪い例: 「トーンはどうしますか？」
良い例: 「冷静×数字中心、熱量控えめがおすすめです。情報商材警戒が強い層なので、断言や煽りより事実と数字で証明する方が信頼を取れます。どう思いますか？」

### 進め方

- ユーザーが答えたら、その答えが生む次の分岐を探して次の問いに進む
- ユーザーが「わからない」と言ったら、推奨案をそのまま採用するか聞く
- 「もう十分」「ここまででいい」とユーザーが言ったら即座に終了する

## Step 4: 終了

終了時は以下の3点だけを短くまとめる。計画書やファイルは作らない。

- **決まった事**: 合意できた決定の箇条書き
- **未決事項**: 詰めきれなかった論点
- **次のステップの候補**: 実装に進む / プラン化する / 追加調査する 等

ユーザーが実装・プラン化を望んだ場合に限り、その段階で plan モードや別スキルに繋ぐ。
